# Portfolio Analytics Tracker — Backend Plan

## 1. Purpose

Implement the backend infrastructure for a first-party, privacy-conscious analytics and visitor-tracking system.

Existing stack:

- Express + Node.js + TypeScript
- Prisma
- MariaDB
- Redis
- Existing authentication
- Existing rate limiting
- Existing Docker deployment

The backend receives anonymous analytics events from the React frontend, validates them, applies privacy controls, stores durable analytics data, aggregates metrics, and exposes protected analytics data to the admin dashboard.

---

# 2. Backend Responsibilities

The backend is responsible for:

- Receiving analytics events
- Validating analytics payloads
- Rate limiting the analytics endpoint
- Creating anonymous visitors
- Creating sessions
- Recording page views
- Recording analytics events
- Processing traffic-source metadata
- Processing coarse geographic metadata
- Processing device/browser/OS metadata
- Aggregating analytics
- Using Redis for short-lived counters/state
- Persisting durable analytics in MariaDB
- Retention/cleanup
- Exposing protected admin analytics APIs

The backend must never trust client-provided analytics data blindly.

# 5. Visitor Identification

Visitors are anonymous.

The backend receives an anonymous visitor identifier generated by the frontend.

Example:

```text
anonymousId = UUID
```

Do not use:

- Email
- Name
- Authentication ID
- Raw IP
- Password
- Any directly identifying information

as the visitor identifier.

The backend should create a Visitor record if the anonymous ID is not known.

For an existing visitor:

```text
lastSeenAt = current timestamp
visitCount = increment when a new session starts
```

---

# 8. Public Analytics Ingestion API

Recommended endpoint:

```text
POST /api/analytics/events
```

Example request:

```json
{
  "visitorId": "anonymous-id",
  "sessionId": "session-id",
  "events": [
    {
      "type": "page_view",
      "path": "/portfolio",
      "timestamp": "2026-08-13T00:00:00.000Z",
      "metadata": {}
    }
  ]
}
```

The endpoint is public because anonymous visitors are not authenticated.

---

# 9. Request Validation

Validate:

- visitor ID format
- session ID format
- event type
- path
- timestamp
- metadata
- maximum event count
- maximum request size

Never accept arbitrary event types.

Never accept unrestricted metadata.

Limit metadata size.

Reject malformed requests.

---

# 10. Rate Limiting

The analytics endpoint must be rate limited.

Reuse the existing rate-limit infrastructure where appropriate.

The endpoint should protect against:

- Event flooding
- Large payload attacks
- Automated abuse
- Excessive requests from a single source

Analytics failures must not affect normal portfolio operation.

# 25. Analytics Metrics

Define metrics clearly.

### Unique Visitors

Unique anonymous visitors in the selected period.

### Sessions

Sessions created in the selected period.

### Page Views

Recorded page-view events.

### Average Session Duration

Average duration for sessions with usable duration data.

### Bounce Rate

Sessions with only one meaningful page view divided by total sessions.

### Contact Conversion Rate

Successful contact submissions divided by the selected, consistently defined visitor/session population.

# 26. Security Requirements

The analytics backend must:

- Validate all input
- Rate limit ingestion
- Limit body size
- Limit event count
- Reject unknown event types
- Sanitize paths
- Sanitize metadata
- Avoid SQL injection through Prisma
- Protect admin analytics endpoints
- Avoid exposing raw analytics records publicly
- Avoid exposing private visitor information
- Prevent analytics endpoints from becoming expensive attack targets

---

# 27. Failure Behavior

Analytics is best effort.

If:

```text
MariaDB unavailable
Redis unavailable
Analytics service unavailable
```

the portfolio must continue functioning.

Do not cause:

```text
page load failure
navigation failure
contact submission failure
game failure
```

because analytics failed.

---

# 28. Performance Requirements

Backend analytics should:

- Accept batches
- Avoid expensive synchronous work
- Use Redis for short-lived counters where useful
- Use database indexes
- Use aggregation for dashboard queries
- Avoid scanning raw event tables unnecessarily
- Keep public ingestion lightweight

---

- Google Analytics

- PostHog

---

# 32. Backend Definition of Done

Backend is complete when:

- Analytics events can be ingested.
- Requests are validated.
- Requests are rate limited.
- Anonymous visitors are created/updated.
- Sessions are created/updated.
- Page views are persisted.
- Portfolio events are persisted.
- Contact conversion events are persisted.
- Analytics data is protected from public access.
- Dashboard APIs return correct aggregates.
- Database growth is controlled.
- Redis is used appropriately.
- Analytics failures do not break the application.
- No unnecessary sensitive visitor information is persisted.
